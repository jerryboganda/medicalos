# Medical Learning OS — 100% Implementation Program (Phases 0–7, nothing left behind)

## Source of truth & how nothing gets left behind

The master plan (`MEDICAL_LEARNING_OS_MASTER_PLAN_v2.md`, 1,555 lines) already defines the phases, gates, and ~120 stable requirement IDs (§29) — each pre-assigned to a phase. The execution program below merges §28 (base phases) + §28.1 (merge additions) + §29 (IDs) + §30 (release gates) + §31 (execution contract) + §32 (open decisions) into one traceable build program.

**Traceability mechanism (created at kickoff, enforced every phase):**
1. `docs/requirements/traceability.md` — every requirement ID from §29 (CORE, QB, EX, AI, PLAN, SR, LIB, NOTE, SIM, IMG, INST, ADMIN, COMMUNITY, CAREER, OFF, OPS, TRUST, UX, PROG, ENG, COMP, COM, GROW, PROT, ARCH) with phase, source section, status (`not-started → in-progress → tested → blocked/deferred`), and acceptance evidence link. No ticket ships without ≥1 ID.
2. `.scratch/phase-0-decisions/` … `.scratch/phase-7-advanced/` — per-phase specs + numbered issue files per `docs/agents/issue-tracker.md` (spec.md + issues/NN-slug.md with Status lines).
3. `docs/requirements/coverage-map.md` — master-plan sections 1–33 + Appendices A–C → phase mapping; a section with no ticket is a gap. Appendix C (Quiz LMS coverage) already proves nothing was dropped in the merge; this proves nothing is dropped in the build.
4. Completion reports distinguish implemented / tested / partial / blocked / deliberately deferred (§31). A mocked integration is never reported as production integration.
5. Every workflow slice follows §31: requirement IDs → data contract → backend → UI → permissions → failure states → tests → evidence → documentation. Non-trivial features run `to-spec` → `tdd` → `implement` → `code-review`; UI runs hallmark; every diff gets `ponytail-review`; debugging starts with `diagnosing-bugs`.

## Operating constraints (hard, already in AGENTS.md)

- **Compute:** all builds/lints/tests/screenshots/analysis/artifacts in GitHub Actions (OPS-01, §27). No builds/tests on the VPS or local machines. Runner matrix per §27.1: Linux (API/workers/crates/WASM/Android), macOS (iOS/macOS, signing/notarization), Windows (desktop). Rust compile caching is mandatory. Device testing via CI-built artifacts → TestFlight / Play internal / approved farm.
- **Runtime boundary (OPS-02):** production deployment is owner-gated (§27 unresolved boundary + §32). Development through Phase 1–2 proceeds in CI with ephemeral Postgres/Redis; the runtime decision ticket runs in parallel and blocks only first real deployment.
- **Rust/Tauri guardrails (§31.1):** Rust types are the contract; generated TS/API client never hand-edited; business rules live in shared crates (never re-implemented in Svelte); no `unsafe` without recorded review; compile-time-checked SQL with tested rollback; narrow capability-scoped Tauri commands; webview never receives secrets/pack keys/unreleased answer keys; shared-crate changes pass native + WASM builds before merge; Swift/Kotlin plugin code is owned and tested; Astro site holds no learner data.
- **Trust rules (§2.3, TRUST-01):** no fake scores/charts/citations/active-agent states; no numerical readiness before Phase 7 validation (owner decision 12); medical answer keys and rights decisions route to the human owner.
